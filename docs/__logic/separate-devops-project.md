# پلن منطقی: جدا کردن پروژه DevOps از پروژه Backend

## سناریو

در حال حاضر همه‌چیز — کد بک‌اند (FastAPI)، فایل‌های اجرا و استقرار
(docker-compose، متغیرهای محیطی) و مستندات — در یک ریپازیتوری گیت واحد قرار
دارند. می‌خواهیم این دو دغدغه را کاملاً از هم جدا کنیم:

1. **پروژه API** — همان پروژه FastAPI فعلی (کد دامنه، اپلیکیشن، زیرساخت،
   presentation، مایگریشن‌ها، مستندات معماری و API). این پروژه فقط مسئول
   منطق و رفتار سرویس حسابداری است و نباید هیچ دانشی درباره‌ی نحوه‌ی
   اجرا/استقرار سایر سرویس‌ها داشته باشد.
2. **پروژه DevOps** — مسئول نحوه‌ی اجرا، ترکیب و راه‌اندازی سرویس‌ها در کنار
   هم (docker-compose، متغیرهای محیطی مشترک، شبکه‌ها، پورت‌ها). این پروژه
   نباید هیچ منطق کسب‌وکاری نداشته باشد و فقط «ارکستراسیون» را نگه می‌دارد.

این دو پروژه هرکدام ریپازیتوری گیت مستقل خودشان را خواهند داشت و به‌صورت دو
پوشه‌ی هم‌سطح، زیر یک پوشه‌ی والد مشترک قرار می‌گیرند.

## هدف / چرایی

- هر تیم (توسعه‌ی بک‌اند در برابر DevOps) بتواند مستقل از دیگری کار کند،
  کامیت بزند و تاریخچه‌ی گیت جدا داشته باشد.
- اضافه‌شدن سرویس‌های جدید در آینده (مثلاً یک پروژه‌ی دیگر، یک سرویس جدید،
  یک دیتابیس دیگر) نباید به تغییر در ریپازیتوری بک‌اند نیاز داشته باشد —
  همه‌ی این‌ها در پروژه‌ی DevOps مدیریت می‌شوند.
- جلوگیری از قاطی‌شدن نگرانی‌های زیرساختی (پورت، شبکه، متغیرهای محیطی
  مخصوص محیط اجرا) با منطق دامنه/اپلیکیشن.

## use caseها

1. یک توسعه‌دهنده‌ی بک‌اند فقط با ریپازیتوری API کار می‌کند؛ نیازی به دیدن
   یا تغییر فایل‌های DevOps ندارد.
2. یک مسئول DevOps می‌خواهد یک سرویس جدید (مثلاً یک پروژه‌ی دیگر در آینده،
   یا یک سرویس کمکی مثل Redis/RabbitMQ) را به مجموعه اضافه کند — این کار
   فقط داخل پروژه‌ی DevOps انجام می‌شود، بدون نیاز به تغییر در پروژه‌ی API.
3. برای اجرای کامل سیستم در محیط توسعه، پروژه‌ی DevOps باید بتواند به کد
   پروژه(های) سرویس (از جمله API) دسترسی داشته باشد تا ایمیج بسازد و آن‌ها
   را اجرا کند — یعنی فرض بر این است که پروژه‌های سرویس (مثل API) به‌صورت
   پوشه‌ی هم‌سطح در کنار پروژه‌ی DevOps روی سیستم توسعه‌دهنده checkout
   شده‌اند.
4. مستندات معماری و API مربوط به سرویس بک‌اند (که در حال حاضر داخل پروژه
   هست) باید همراه پروژه‌ی API بماند، چون به کد و رفتار همان سرویس مربوط
   است.
5. مستندات و پلن‌های مربوط به کار روی سرویس بک‌اند (پلن منطقی/فنی هر تسک)
   باید همراه همان ریپازیتوری‌ای بمانند که آن تسک روی آن انجام می‌شود —
   یعنی اگر تسک مربوط به بک‌اند است، پلن‌هایش در ریپازیتوری API ذخیره
   می‌شود؛ اگر تسک مربوط به DevOps است (مثل همین تسک)، پلن‌هایش باید در
   ریپازیتوری DevOps ذخیره شوند.

## نکات و edge caseها

- تاریخچه‌ی گیت فعلی (کامیت‌های قبلی پروژه) باید برای پروژه‌ی API حفظ
  شود؛ این پروژه فقط جابه‌جا می‌شود، ریپازیتوری‌اش از نو ساخته نمی‌شود.
- پروژه‌ی DevOps یک ریپازیتوری کاملاً تازه است (بدون تاریخچه‌ی قبلی) و
  فقط به‌صورت لوکال (`git init`) ساخته می‌شود؛ اتصال به یک ریموت (مثل
  گیت‌هاب) بعداً و به‌صورت جداگانه انجام خواهد شد.
- بعد از این جداسازی، پروژه‌ی API دیگر نباید هیچ فایل مربوط به
  ارکستراسیون (مثل فایل docker-compose یا متغیرهای محیطی مشترک بین
  سرویس‌ها) را در خودش نگه دارد.
- فایل‌های مخصوص ساخت ایمیج خود سرویس (Dockerfile سرویس API) همچنان باید
  داخل خود پروژه‌ی API بماند، چون این فایل مربوط به «چگونگی ساخت همین
  سرویس» است، نه ارکستراسیون بین سرویس‌ها. تصمیم دقیق درباره‌ی جزئیات این
  مورد در پلن فنی مشخص می‌شود.
- این تغییر ساختاری، هیچ تغییری در رفتار یا منطق کسب‌وکاری سرویس حسابداری
  ایجاد نمی‌کند؛ فقط محل قرارگیری فایل‌ها و مرز بین دو ریپازیتوری را عوض
  می‌کند.

## در انتظار تایید

پس از تایید این پلن منطقی توسط شما، پلن فنی (به انگلیسی، شامل جزئیات دقیق
دستورها، مسیرها و فایل‌ها) نوشته و در `docs/__plan/` ذخیره خواهد شد و تنها
پس از آن تغییرات واقعی روی فایل‌ها اعمال می‌شود.
